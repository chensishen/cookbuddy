# AGENT 任务书：修复“依赖固定句式”问题，建立“模型理解、程序校验”的容错链路

> 面向执行修复的 AI 编码 Agent。整份文档作为任务输入：先复现问题、盘点现状，再按第 12 节阶段推进，每阶段通过验收后再进入下一阶段。
> 约定：**MUST / MUST NOT** 为硬性要求；**SHOULD** 为默认做法，有充分理由可调整并在 PR 说明中写明。

---

## 0. 问题背景（已由前序排查确认，实施前需自行复现）

用户反馈：日常问答经常出问题；不按“规定句式”提问，或提问中有错字 / 多余字符，就会失败。
排查结论：**规则承担了过多语言理解工作，模型没有充分承担理解口语、识别笔误和结合上下文的职责；本应只用于“核实菜谱事实”的严格机制，被扩大到了普通对话和输入理解上。**

三个已定位的例子（路径来自前序排查，**行号可能已变，以实际代码为准**）：

| # | 用户输入 | 现象 | 根因位置 |
|---|---|---|---|
| 1 | “你是谁” | 得到“检索资料不足” | `src/agent/engine.py`（约 161 行）：日常问答入口只匹配“你好”“你能帮我做什么”等少数固定表达；未命中的问题进入菜谱流程，且后续流程**还会补做菜谱检索** |
| 2 | “只看酵头制作部分” | 匹配失败；而“只看酵头制作”成功 | `scripts/recipe_tools.py`（约 114 行）：把提取出的“酵头制作部分”当作**精确章节名**去匹配“酵头的制作”，多了“部分”就失败 |
| 3 | “不要刚才第二道1”（末尾多一个“1”） | 去掉“1”能识别，加上后整句被判为“未识别条件”，推荐模块直接停止返回 | 条件解析把无法识别的片段视为**致命错误**，推荐模块遇到未识别条件即终止 |

共同模式：**规则门（gate）在模型看到输入之前就拒绝或误导了请求；遇到不认识的内容时选择“失败”而不是“降级”。**

## 1. 目标与非目标

**目标**
1. 先**理解意图**，再由程序**校验菜谱依据与约束**。
2. 对口语后缀、多余字、错别字、全半角、标点、空格、简繁等**无关紧要的偏差容错**。
3. 只有**歧义确实会影响结果**时才追问，且一次只问一个问题。
4. 普通对话（问身份、问能力、闲聊）**不进入菜谱检索与“资料不足”流程**。
5. 规则从“门”降级为“快速通道 + 兜底 + 校验”。

**非目标**
- 不放松**菜谱事实**的依据要求（步骤、用量、原料仍必须来自检索到的原文）。
- 不放松安全类硬约束（过敏、忌口的代码层过滤保持不变）。
- 不重写检索 / rerank / 记忆核心；只改它们**前面的理解层**和**后面的降级行为**。

## 2. 设计原则

1. **模型负责理解，程序负责校验。** 意图、槽位、指代由模型解析；程序检查结果是否合法、是否有依据、是否违反约束。
2. **未知内容降级，不致命。** 任何规则无法处理的输入，必须回落到模型理解或通用对话，**不得直接报错或拒答**。
3. **严格校验只用于事实性输出。** “资料不足”只能出现在“用户在问菜谱事实且检索确实无依据”时。
4. **容错优先于追问，追问优先于失败。** 能高置信度推断就直接做并说明所做的假设；有实质歧义才问；永远不静默失败。
5. **不靠加句式修复。** 禁止通过继续增加固定问法 / 关键词来“修好”个别例子。

## 3. 硬性规则（MUST / MUST NOT）

1. 用户输入 **MUST** 先经过“规范化 + 意图路由”，**MUST NOT** 在此之前被任何关键词 / 正则 / 精确匹配规则拒绝。
2. 意图路由器无法判断或调用失败 / 超时时，**MUST** 回落到：规则兜底路由 → 仍未知则走“通用对话”或“带原句的菜谱检索”，**MUST NOT** 返回错误或空结果。
3. 非菜谱意图（身份、能力、闲聊、问候、致谢）**MUST NOT** 触发菜谱检索，**MUST NOT** 产生“检索资料不足”类回答。
4. 章节名、菜名、食材名的匹配 **MUST** 使用分级容错匹配（见 6），**MUST NOT** 使用单一精确匹配作为唯一手段。
5. 条件解析中出现“未识别片段”时，**MUST** 走第 7 节策略（忽略 / 追问 / 回落），**MUST NOT** 因此终止推荐流程。
6. 对菜谱事实的回答 **MUST** 继续满足：依据来自检索原文、附引用；找不到才说“知识库中没有找到”。
7. 追问 **MUST** 满足第 8 节条件，且一次只问一个问题、给出可点选的选项。
8. 低置信度匹配（中等分数）**MUST** 以“我按「X」理解了，不对请告诉我”的方式透明说明；**MUST NOT** 悄悄替换用户意图。
9. 每个被保留的规则门 **MUST** 在 `docs/gate_inventory.md` 中登记保留理由。
10. 日志 **MUST NOT** 输出用户原文（只记意图、置信度、匹配分、路径、耗时）。

## 4. 目标架构

```
用户输入
  → ① 输入规范化（程序，确定性）
  → ② 快速通道（可选）：精确命中的高频固定表达（问候/致谢），直接路由
  → ③ 意图路由器（小模型，结构化输出）：intent + slots + confidence + needs_clarification
  → ④ 槽位解析与容错匹配（程序）：菜名/章节/食材模糊匹配、条件解析、指代消解
  → ⑤ 澄清策略（程序）：判断是否真的需要追问
  → ⑥ 执行分支（按 answer_mode）
        grounded_recipe  → 检索 + 校验依据 + 带引用回答
        general_chat     → 直接回答（身份/能力/闲聊），不检索
        clarify          → 一句追问 + 选项
        out_of_scope     → 礼貌说明边界并引导回菜谱
  → ⑦ 校验层（程序）：硬约束、依据检查、引用格式
```

**分工线**：①②④⑤⑦ 是程序（确定性、可测试）；③ 是模型（理解）；**规则只在 ②（快速通道）与 ④⑦（校验）出现，不再出现在“入口拒绝”的位置。**

## 5. 意图路由器（③）

### 5.1 意图集合

| intent | 说明 | answer_mode |
|---|---|---|
| `chitchat` | 问候、致谢、闲聊 | general_chat |
| `identity_capability` | 你是谁 / 你能做什么 / 怎么用 | general_chat |
| `recipe_lookup` | 查某道菜的做法 / 原料 | grounded_recipe |
| `recipe_section` | 只看某章节（原料 / 操作 / 计算 / 酵头制作等） | grounded_recipe |
| `ingredient_recommend` | 按食材推荐 | grounded_recipe |
| `constraint_refine` | 换一个 / 不要第N道 / 更清淡 / 更简单 | grounded_recipe |
| `preference_update` | 记住 / 忘掉偏好 | （交给记忆管线） |
| `follow_up` | 依赖上文的追问（“那它要什么调料”） | grounded_recipe |
| `out_of_scope` | 与做菜无关的请求 | out_of_scope / general_chat |
| `unclear` | 无法判断 | clarify 或回落（见 8） |

> 以仓库现有意图为准做映射，不要求一次性替换全部；但 **`chitchat` 与 `identity_capability` 必须新增**。

### 5.2 输出 schema（强制 JSON，温度 0）

```json
{
  "intent": "recipe_section",
  "confidence": 0.0,
  "slots": {
    "dish": "酵头面包",
    "section": "酵头的制作",
    "ingredients": [],
    "exclude_refs": [],          // 如 [{"type":"ordinal","value":2}]
    "constraints": {"max_difficulty": null, "category": null, "taste": null},
    "raw_noise": ["部分"]        // 模型认为无意义的多余片段
  },
  "needs_clarification": false,
  "clarify_question": null,
  "assumptions": ["把“酵头制作部分”理解为章节“酵头的制作”"]
}
```

### 5.3 Prompt 要点（`prompts.py`）

```
你是做菜助手的意图理解器。用户输入可能含错别字、口语、多余的字或符号、全半角混用，请按“最可能的意图”理解，不要因为措辞不规范而判为 unclear。
任务：输出 intent、slots、confidence、是否需要澄清。
规则：
1. 问身份、能力、打招呼、闲聊 → chitchat / identity_capability，不涉及菜谱检索。
2. 提到某道菜/某个章节 → 提取 dish / section；“部分、那段、的、一下、看看、只看”等词不是章节名的一部分，放进 raw_noise 或忽略。
3. 末尾多余的数字、标点、语气词视为噪声，除非它与“第N”等结构连用。
4. 引用上文（第二道、刚才那个、换一个）→ 填 exclude_refs 或 follow_up，不要追问已能从上下文确定的内容。
5. 只有“不同理解会导致明显不同结果”时 needs_clarification 才为 true，并给出一句简短问题。
6. 不要回答问题本身，只输出 JSON。
【最近对话摘要与槽位】{context}
【用户输入】{user_input}
```

### 5.4 调用约束
- 使用小而快的模型；超时 3 s（可配置）；失败重试 1 次；仍失败 → 规则兜底路由（见 9）。
- 与已有的 Query 改写合并为**同一次调用**（避免多一次 LLM 延迟）；上下文只传摘要 + 槽位 + 最近 2 轮。
- 对相同输入做短期缓存（key = 规范化输入 + 上下文哈希）。

## 6. 规范化（①）与容错匹配（④）

### 6.1 输入规范化 `normalize(text)`（确定性）
- Unicode NFKC（全半角统一）、去首尾空白、合并连续空白；
- 统一标点（中英文标点归一，**去除末尾孤立标点与表情**）；
- 繁转简（可选）；
- **去除“孤立噪声”**：句末独立的数字 / 符号（如“……第二道1”末尾的“1”）——**仅当**它不与“第”“个”“道”“号”等序数结构相连时才去除；拿不准时保留原文并交给路由器判断。
- 规范化结果**同时保留原文**，路由器看到的是“规范化文本 + 原文”。

### 6.2 名称容错匹配 `fuzzy_match(query, candidates)`

适用于：章节名、菜名、食材名。候选集来自内存索引（菜名几百个、章节名几十个，成本很低）。

**分级阶梯（命中即停，记录命中级别与分数）**

| 级别 | 方法 | 说明 |
|---|---|---|
| L0 | 精确匹配 | |
| L1 | 规范化精确匹配 | 去标点、去**填充词**后再比 |
| L2 | 包含 / 词元重叠 | “酵头制作” ⊂ “酵头的制作”（先去掉“的/之/部分/章节/那段/一下”等填充词再比较） |
| L3 | 字符 n-gram / 编辑距离（如 `rapidfuzz`） | 处理少字多字、笔误 |
| L4 | 拼音相似（如 `pypinyin`） | 处理同音错别字 |
| L5 | 向量相似（复用已有 embedding） | 处理同义改写 |
| L6 | 把 Top-3 候选交给模型消歧 | 仅在 L3–L5 结果接近时使用 |

**决策规则**
- `top1 ≥ T_high` 且 `top1 − top2 ≥ margin` → **直接采用**；
- `T_mid ≤ top1 < T_high` 或差距小 → 采用 top1，但在回答开头**透明说明**所做的理解；若两个候选会导致明显不同结果 → 走澄清（第 8 节）；
- `top1 < T_mid` → 判定为“未找到”，回答“知识库里没有找到相近的「…」”，并可给出 2–3 个最相近候选供选择，**不得静默失败**。
- 阈值初始值：`T_high=0.88, T_mid=0.65, margin=0.08`（以评测集标定，写入配置）。

**填充词表**（配置化，可扩充，**不是固定问法**）：`部分 章节 那段 那一段 一下 一点 看看 只看 的 之 吧 呢 啊 哦 请 帮我 我想 我要`。它只用于“匹配前清洗”，不得用于决定意图。

### 6.3 章节匹配的特殊处理
- 章节名来源：该菜谱的 `heading_path / section` 元数据（见 RAG 任务书）；
- 用户说“只看X”时：先确定菜（若上文已有 `selected_dish` 则直接用），再在该菜的章节名中做 6.2 的匹配；
- 未指定菜且无上下文：追问“你想看哪道菜的「X」？”（合法追问，见 8）。

## 7. 条件解析与未识别片段策略（④）

**现状问题**：未识别片段被当作致命错误，推荐模块直接停止。
**新策略**：

1. 条件由路由器输出为结构化槽位（`exclude_refs / constraints / ingredients`），程序**校验合法性**而不是自己用正则猜。
2. 路由器标记的 `raw_noise` 与规范化后残留的片段统一记入 `ignored_tokens`，**不影响执行**。
3. 对**未能映射到任何已知槽位**的残留片段，按影响面分三类处理：

| 类别 | 判定 | 处理 |
|---|---|---|
| 无影响 | 去掉后条件与不去掉**完全一致**（可通过“去掉后重解析并比较结果”验证） | 忽略，继续执行 |
| 可能有影响但可推断 | 例如“第二道1”可能是“第二道”或“第1道” | 取置信度最高的解释执行，并说明理解（“我按『不要第二道』处理”） |
| 确有歧义且影响结果 | 不同解释导致不同推荐 | 走澄清，一次一个问题 |

4. **任何情况下推荐模块 MUST NOT 因未识别条件而终止**；最差情况是“忽略该片段并说明”，或“提出一个澄清问题”。
5. 指代消解（第 N 道、刚才那个、换一个）使用会话槽位 `last_recommendations`（见记忆 / LangChain 任务书），**由程序解析，不交给自由文本匹配**；序数超出范围 → 说明“刚才只推荐了 3 道”，并给出选择。

## 8. 澄清策略（⑤）

**允许追问的情形（满足其一才可追问）**
- A. 多个候选**分数接近**，且选择不同会得到**明显不同**的回答；
- B. 必需槽位缺失，且**无法从上下文 / 记忆推断**（如“只看酵头制作”但未指定菜、上文也没有）；
- C. 高风险操作（删除 / 放宽硬约束、清空记忆）——沿用记忆任务书的确认规则；
- D. 路由器 `confidence < T_route` 且 `intent=unclear`，同时回落策略（9）也无法给出有用回答。

**追问格式**：一句话 + 2–4 个选项；不堆问题；用户忽略则按最可能的理解继续（若可行）。

**禁止追问的情形**
- 仅因措辞不规范、多余字、错别字（能高置信度还原）；
- 问题可以先给出“部分答案 + 说明假设”；
- 已在会话槽位 / 记忆中有答案。

**“假设透明化”模板**：回答开头一句话：`我按「{理解}」帮你处理了，如果不是这个意思告诉我。`（仅在使用了中置信度匹配或忽略了可能有影响的片段时出现）。

## 9. 兜底链路（保证不被规则“卡死”）

```
意图路由器（模型）
   ├─ 成功且置信度≥阈值 → 按 intent 执行
   ├─ 低置信度 → 规则兜底路由（保留的关键词/正则，仅作“提示”）
   │        ├─ 命中 → 执行（并在 trace 中标记 fallback=rule）
   │        └─ 未命中 → general_chat（若像闲聊/身份）或 带原句的 grounded_recipe 检索
   └─ 超时/异常 → 同上兜底
最终仍无结果 → “没太理解，你可以告诉我想做什么菜或有哪些食材吗？”（友好的固定话术，不报错、不说“检索资料不足”）
```

`“检索资料不足”` **只允许**出现在：意图为菜谱事实类 且 检索确实无相关依据。

## 10. 需要改动 / 盘点的现有位置

**阶段 0 必做：规则门盘点**
在仓库中搜索所有“用规则决定放行 / 拒绝 / 路由”的位置（如 `startswith`、`in`、`==`、`re.match/search`、固定字典 / 列表查表、`if text in {...}`、`raise` 于未识别分支等），产出 `docs/gate_inventory.md`，每条登记：文件:行、规则内容、作用、**处置**：

| 处置 | 标准 |
|---|---|
| 保留 | 属于**校验 / 安全 / 确定性**需求（硬约束过滤、输入长度限制、权限、引用格式） |
| 降级为兜底 | 可作为模型失败时的回落（关键词路由、固定问法） |
| 降级为提示 | 作为特征传给路由器（如命中词表 → `hint`），不直接决定结果 |
| 删除 | 只会造成误拦的“入口门” |

**已知必须处理的三处**
1. `engine.py` 日常问答入口：固定表达匹配 → 改为路由器 + 快速通道；删除“非命中即进入菜谱流程并补做检索”的行为；新增 `general_chat` 分支（身份 / 能力 / 闲聊走通用回答，不检索）。
2. `recipe_tools.py` 章节读取：精确章节名匹配 → 6.2 分级容错匹配。
3. 推荐模块 / 条件解析：未识别条件即停止 → 第 7 节策略。

```yaml
fallback:
  rule_router: true
  friendly_unknown_message: "没太理解你的意思，可以告诉我想做什么菜，或者手边有哪些食材吗？"
```

## 12. 实施阶段与验收

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| S0 | **复现**三个问题并写成**失败的**回归测试；运行基线鲁棒性评测并保存**基线报告**；产出 `gate_inventory.md` | 三个测试在修复前红；基线数字由脚本产出 |
| S1 | 规范化 + 分级容错匹配 + 填充词配置；替换 `recipe_tools.py` 章节匹配、菜名 / 食材匹配 | T-N1~T-N8 |
| S2 | 意图路由器 + `general_chat` 分支 + 快速通道 + 兜底链路；改造 `engine.py` 入口 | T-R1~T-R8 |
| S3 | 条件解析重构（第 7 节）；推荐模块不再因未识别条件终止 | T-C1~T-C6 |

| S5 | 鲁棒性评测集、扰动测试、与基线对比报告、文档 | T-E1~T-E3，指标达标 |

每阶段结束：运行全部已有测试；并对 RAG 评测集跑一次，**菜谱事实类问题的依据与引用准确率不得下降**（下降超过 1 个百分点需说明）。

### 12.1 验收测试用例

**必过的三个回归（修复目标）**
- **T-R1** “你是谁” → `intent=identity_capability`，走 general_chat，**不触发检索**，回答自我介绍与能力，不含“检索资料不足”。
- **T-N1** “只看酵头制作部分”（上文已选定对应菜）→ 匹配到章节“酵头的制作”并返回该章节内容，与“只看酵头制作”结果一致。
- **T-C1** “不要刚才第二道1” 与 “不要刚才第二道” → 推荐结果一致（排除第二道），不因“1”终止；`ignored_tokens` 记录“1”。

**规范化与容错匹配（T-N）**
- **T-N2** 填充词变体：“酵头制作那一段 / 看看酵头制作 / 酵头的制作部分吧” → 同一章节。
- **T-N3** 错别字：“酵投制作”“红烧rou”“西红是炒蛋” → 在菜名 / 章节候选中被匹配（L3/L4），且在中置信度时有“我按…理解”的说明。
- **T-N4** 全半角、多空格、末尾标点 / 表情：结果不变。
- **T-N5** 同义改写（“怎么发酵头”）→ 通过向量级匹配命中，或进入 L6 消歧。
- **T-N6** 候选分数接近（两个章节都像）→ 触发澄清（A 类），**只问一个问题且带选项**。
- **T-N7** 完全无关的名称（候选分数低）→ 回答“知识库里没有找到相近的「…」”，并给出 2–3 个最相近候选；不报错。
- **T-N8** 规范化不得破坏有意义的数字：“第2道”“放3个鸡蛋”保持原样。

**路由与回答模式（T-R）**
- **T-R2** 问候 / 致谢 / 闲聊变体（“嗨”“在吗”“谢啦”“你叫啥”“介绍一下你自己”）→ general_chat，均不检索。
- **T-R3** 路由器超时 / 抛异常 → 回落规则路由；仍未命中 → 友好兜底话术或带原句检索，**不返回错误**。
- **T-R4** 非菜谱问题（“今天天气怎么样”）→ out_of_scope 的礼貌说明并引导回做菜，不说“检索资料不足”。
- **T-R5** 菜谱事实类问题检索确无依据 → 回答“知识库中没有找到”，**此时才允许**“资料不足”类表述。
- **T-R6** 菜谱事实回答仍带引用（菜名 / 章节 / 路径）；依据校验未被削弱。
- **T-R7** 日志中不包含用户原文。
- **T-R8** 快速通道命中与否不改变最终结果（关闭快速通道，结果相同，仅延迟不同）。

**条件解析（T-C）**
- **T-C2** “不要第二道”“别要第 2 个”“第二个不要了”→ 同一排除。
- **T-C3** 序数超出范围（只推荐了 3 道却说“第五道”）→ 说明范围并给选项，不终止。
- **T-C4** 未识别片段“无影响”类（如“哈哈”“啦”）→ 忽略并继续。
- **T-C5** 确有歧义（“不要第二道1”，且存在“第1道”的合理解释，两种解释结果不同）→ 取最高置信解释并透明说明，或澄清；**不得终止**。
- **T-C6** 推荐模块单元测试：向其传入含未知条件的输入，**不抛异常、不提前返回空**。

**澄清策略（T-Q）**
- **T-Q1** 仅有错别字 / 多余字（可高置信还原）→ **不追问**。
- **T-Q2** 需要的菜名缺失且上下文无 → 追问一次，一句话 + 选项。
- **T-Q3** 一轮最多一个问题。
- **T-Q4** 用户忽略澄清继续提问 → 按最可能理解继续，不重复追问。
- **T-Q5** 高风险（解除硬约束）仍走确认流程，不被“少追问”原则削弱。

**评测与鲁棒性（T-E）**
- **T-E1** 鲁棒性评测集 `nlu_robust_v1.jsonl` 一键运行，输出报告（含基线对比）。
- **T-E2** 扰动测试：对黄金集中每条标准问法自动生成扰动版本（见 13），**意图与槽位准确率下降不超过阈值**。
- **T-E3** 误拦率（应回答却被拦 / 被判“资料不足”）与不必要追问率达到目标。

## 13. 鲁棒性评测集与指标

**构建 `eval/nlu/nlu_robust_v1.jsonl`（约 150–200 条）**，每条：`input`、`context`（可选槽位 / 上一轮）、`gold_intent`、`gold_slots`、`should_clarify`、`should_retrieve`、`category`。

| 类别 | 覆盖 |
|---|---|
| 日常对话 | 身份、能力、问候、致谢、闲聊的多种说法 |
| 章节读取 | “只看X / 看看X / X那一段 / X部分”等 |
| 菜名与食材 | 标准名、别名、错别字、同音字、少字多字 |
| 条件与指代 | 第N道、刚才那个、换一个、排除、更清淡，含噪声数字 / 标点 |
| 无关紧要的噪声 | 全半角、空格、emoji、语气词、末尾符号 |
| 确有歧义 | 应追问的样例 |
| 库外 / 无依据 | 应回答“没有找到”的样例 |

**扰动生成器（程序化）**：对标准问法随机应用：加语气词 / 口语后缀、加末尾数字或符号、全半角互换、插入空格、替换同音字、删 / 加一个字、繁简转换。固定随机种子，扰动结果可复现。

**指标（均由脚本产出）**
| 指标 | 定义 |
|---|---|
| 意图准确率 | 路由 intent 与 gold 一致的比例（分类别） |
| 槽位 F1 | dish / section / exclude_refs / constraints 的匹配 |
| **误拦率** | 应正常回答但被拒绝 / 返回“资料不足” / 返回错误的比例（本次问题的核心指标） |
| 不必要追问率 | 不该追问却追问的比例 |
| 应追问召回率 | 真正歧义时确实追问的比例 |
| 扰动稳定性 | 扰动版本与原版本**结果一致**的比例 |
| 事实类依据 / 引用准确率 | 保持不下降（回归保护） |
| 延迟 / 成本增量 | 路由器调用带来的 P50 / P95 与 token 增量 |

**目标阈值（初始，可调整）**：误拦率 ≤ 2%；扰动稳定性 ≥ 95%；不必要追问率 ≤ 5%；日常对话意图准确率 ≥ 98%；P95 延迟增量 ≤ 500 ms（路由器小模型 + 缓存 + 快速通道）。
**必须先跑基线**：S0 在**未修改的代码**上跑评测并保存报告，最终报告对比修复前后；**不要预填或编造任何数字**。

## 14. 禁止事项

- **不要通过继续增加固定问法 / 关键词 / 正则来修复个别例子。**
- 不要为通过测试而在代码里写死测试输入或特判三个已知例子。
- 不要在模型理解之前设置会拒绝请求的规则门。
- 不要让未识别内容直接导致报错、终止或“资料不足”。
- 不要放松菜谱事实的依据与引用要求；不要放松硬约束的代码层过滤。
- 不要让模型决定事实内容或权限（模型只做理解，事实来自检索，权限来自上下文）。
- 不要一次追问多个问题；不要为措辞不规范而追问。
- 不要静默替换用户意图（中置信度必须透明说明）。
- 不要吞掉异常；降级必须在 trace 中标记（`fallback=rule/general_chat`）。
- 不要在报告里填写未经脚本产出的指标；不要在日志里输出用户原文。
