# 一餐规划修复与验收

日期：2026-10-19。

用户问题：“两个人吃晚饭，30分钟内做好，推荐两菜一汤。”

原链路将菜单规划交给普通推荐状态解析，改写成“请推荐2道菜”，随后路由到普通RAG；人数、整餐时间、汤的数量留在未结构化文本中，并加入历史辣味条件。最终显示“资料不足”。此问题是任务解析和路由错误，不能据此判断知识库缺少菜谱。

## 实现

- 菜汤组合和一餐规划先于普通推荐解析，保存人数、总时间、菜数、汤数；直接路由到 `meal_planner`。
- 按菜谱分类分别选菜和汤，重用已有原文核对及硬限制过滤，不将历史辣味软偏好强制加成菜单的检索门槛。
- 只使用菜谱简介里的整道菜耗时估计；小时和分钟合并计算、区间取上限；孤立的焖煮时间、至少时长、无法解释的时间不作为完成依据。
- 组合按各菜原文总耗时相加，避免假定双灶、多人并行。人数用于共食菜单，未猜测配方克数或自动翻倍，份量变化和主食时间明确说明。
- 数量缺失采用两菜一汤的明确默认结构；缺人数、缺时间、未知条件或时间无法满足时给出具体澄清，不输出通用“资料不足”。价格预算和仅有库存的核算尚未支持，明确提示，不静默丢弃。
- 菜谱卡片重用现有介绍、推荐理由、食材与图片布局。来源带原文行号，并验证记录JSON/Markdown导出成功。

主要文件：`scripts/cookbuddy/meal_planning.py`、`task_context.py`、`router.py`、`pipeline.py`；`scripts/preference_recommendation.py`新增可选分类及候选池参数，默认行为不变。

## 验收

- 全量后端（开启真实PostgreSQL/Milvus集成）：477项通过，38.600秒。
- 前端渲染：22项通过；本轮未改前端代码。
- 新增5项规划模块测试，覆盖结构、独立路由、原文引用、记录导出、缺失/未知条件、整餐时间、时间区间及小时、硬限制及当前食材排除。
- 新增1项真实集成测试：用户已有辣度画像，完整请求仍直接规划两菜一汤，不回退到通用RAG；菜单记录写入会话，三道选择可继续指代。
