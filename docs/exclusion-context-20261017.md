# 连续选菜中的食材排除条件修复

## 问题与原因

复现链路：我喜欢吃辣的，给我推荐3道菜 → 我有鸡肉 → 不要带辣椒的。

第三轮虽然识别为条件补充，却把排除要求存进 `extra_constraints` 原始文字；推荐器不能执行该字段，退回普通 RAG，旧辣味偏好也没有消除。最终出现笼统的资料不足或校验失败。

## 本次处理

- 任务状态增加可选 `excluded_ingredients`，兼容已有 version=1 状态；按食材槽更新，不将食材排除误认为增加辣味偏好。
- 排除、取消排除、替换主食材、数量和做法条件分别处理；支持常见否定表达、多个食材、连续累加、重复提交及部分逗号分隔组合。
- 新的辣椒排除覆盖旧的正向辣味偏好，保留鸡肉、数量、其他排除项；不据此声称成菜必然“不辣”。取消排除不会自动恢复已经取消的旧辣味偏好。
- 原文筛选检查完整当前文件，包括可选材料及操作，不仅检查检索片段。辣椒采用保守家族过滤，包含青红椒、辣椒油、剁椒、豆瓣酱等已识别关联项。
- 有排除要求时，保守过滤成分未注明的已识别复合调料，例如奥尔良腌料、盐焗鸡粉、咖喱、调料包。不提供“从原配方删掉某料就可行”的结论。
- 返回的卡片继续包含菜品介绍、推荐理由、主要用料；摘要显示当前筛选条件。无候选时解释具体条件，不返回泛化的“检索章节没提供信息”。
- 未支持的短否定条件进入澄清，保留原选菜状态；不静默清空条件，也不进入注定失败的事实问答流程。
- 对旧失败状态中单独保存的、可完整识别的食材排除文字，在读取时转换为结构化条件；不改写旧消息。
- 烤盘、铝箔不再混入主要用料。

## 实际边界

食材名称及别名采用有界规则，尚非任意自然语言条件的完整语义理解。未知短条件会澄清；明确推荐请求中的过敏、低盐、人数等复杂要求仍保留给原有流程。原文未列出某食材不能证明商品的全部成分或厨房交叉接触情况，输出因此限定为“原文未列出”及“已识别的相关制品”，不提供过敏安全保证。保守过滤可能减少候选数量。

历史失败若已经丢失全部任务状态，无法可靠重建旧条件，需要用户重新明确推荐要求；仍保有任务状态及原始排除条件的失败对话可继续。
