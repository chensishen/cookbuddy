# 选菜上下文重构与真实对话验收

## 本次真实故障

数据库中的用户原话为：

1. 我喜欢吃辣的，给我推荐3道菜。
2. 我有鸡肉。
3. 我不吃辣椒
4. 不要带辣椒

第三轮原实现虽然抽出了“不吃辣椒”，剩余主语“我”却让另一段完整匹配逻辑拒绝继续任务。失败助手记录的 task_context 被保存为 null；第四轮只读取最后一条助手记录，因而无法恢复条件。随后自由文本改写又混入用户这次未提出的“不吃香菜、我是新手”。

此前修复只测了省略主语的表达，没有覆盖这条完整故障链路，因此不能证明问题已经解决。

## 重构范围

### 1. 完整分句解析

`scripts/cookbuddy/recommendation_turn.py` 只解释本轮话语，输出带原话依据的 Edit（操作、字段、值），不读取或修改任务状态。

- 将主语、时间词、连接词、否定词、食材列表、推荐数量作为语法处理；主语和时间词支持交换顺序。
- 食材排除优先解析完整目标；不通过“出现辣字”推断辣味。
- 同一句中的多项修改按顺序解释。
- 每个分句必须被完整消费，或明确列为 unresolved，不能忽略剩余文字。

### 2. 独立状态更新

`scripts/cookbuddy/task_context.py` 负责纯状态更新，`recommendation_schema.py` 负责状态与词表约束。

- 验证操作类型、字段、允许值和数量；整轮修改原子应用，失败不留下半套条件。
- 最新食材排除清除冲突的旧偏好；换主食材、恢复某项配料、排除做法分别处理。
- 不明确的短修改澄清并保留原条件；明确独立菜谱和新话题关闭旧任务。
- 无法解析的明确推荐分句保留原话交给已有复杂流程；超过状态长度上限则澄清，不截断限制。
- 输出保留版本和 Edit 记录，便于检查究竟改了哪些条件。

### 3. 用户轮次上的持久状态

新增迁移 `004_conversation_task_states.sql` 和 PostgreSQL 表 `cookbuddy.task_states`，本机已应用。

- 用户条件解析完成后、模型及工具运行前写入任务状态。助手生成失败不再清空条件。
- 推荐成功后，只为同一用户轮次补充实际展示的候选项。
- 读取以当前用户消息 ID 为截止点。迟到的旧轮次不会覆盖新轮次，后来的状态也不能倒流到旧请求。
- 显式关闭状态作为边界保存，不能恢复已经结束的任务。
- RLS 及复合外键约束用户、会话和对应用户消息，防止跨用户或跨会话关联。
- 已有旧对话：当旧失败记录丢失状态时，在当前会话内按最多 200 条历史消息重放用户原话；助手记录仅提供有原文验证的已展示候选项，不采用模型改写的条件。重放保留显式话题边界，不写回旧消息。

### 4. 推荐执行

已解析的任务直接进入已有条件筛选。继续使用完整当前菜谱的食材及操作核对，不调用事实问答去回答一条条件声明；也不让长期记忆自由改写已明确的当前条件。

## 使用与边界

本机迁移已经完成，新请求直接使用新版；用户可在原失败会话继续说“不要带辣椒”，旧失败消息本身不会自动变成成功结果。

其他部署升级需先运行 `python scripts/cookbuddy_manage.py init`。本次采用有界分句语法和显式状态，不声称理解所有自然语言限制；未知修改会澄清。复杂营养、过敏、预算等请求仍属于已有复杂流程。本次不改变长期记忆提取、向量库和菜谱事实校验规则。
