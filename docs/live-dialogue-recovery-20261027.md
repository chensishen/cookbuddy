# 模型恢复后的真实对话复验（2026-10-27）

模型已恢复可调用。本轮根据成功探测结果，只解除当前模型对应的旧共享冷却记录，保留其他供应商状态；写入 `manual_recovery` 事件。随后通过正常治理链路请求成功，耗时1.19秒，没有修改凭证或关闭限流保护。

## 真实复验发现与修复

- “推荐两道菜，同时列缺料”被错误当作已有菜谱的原料追问：执行顺序改为先尊重推荐意图，再处理附带的食材输出要求。
- 单道替换带入整批数量时，页面多显示了一个新候选：单道替换固定只取一个替代结果，持久列表只更新对应位置。
- 模型把 `replace_ref` 返回为 `{"type":"ordinal","value":1}`，原接口只接受整数，导致正确意图降级：边界层接受这个严格等价的序号表示。字符串、布尔值、额外字段仍拒绝，越界仍澄清。
- 食材记忆的旧关键词识别漏掉“挑两道菜”，记录通知抢占回答：模型已明确识别做菜任务时，普通 `SESSION_ONLY/QUEUED` 通知不再终止任务；需要确认的记忆操作继续保留。无模型支持的单纯库存记录保留原行为。
- “第二道”的章节请求在解析序号之前追问菜名：先绑定列表来源，再核对章节；明确请求原文但章节为空时返回完整原文，不追问可选章节。
- 模型失败后的序号追问被误提取为菜名“第二道的”：仅在规则兜底阶段，抽取唯一的列表序号并由程序校验，继续绑定实际来源。
- 部分请求超过3秒导致正常理解被打断：单次理解预算调整为5秒，仍最多重试一次；准备阶段配套调整为16秒，整体请求上限仍为30秒。这会允许部分请求等待更久，不保证供应商不会再次超时或限流。

提示要求明确区分替换、排除和重新推荐，列表顺序以持久槽位为准。这些要求描述操作语义，不要求用户使用某个固定问句。
