# 2026-10-28 理解服务熔断与餐次降级事故（S0）

本结论在修改熔断策略之前记录。证据来自本地运行事件库，统计窗口为上海时间 2026-10-28 00:40–00:52；未复制用户原文、认证头或密钥。机器可核对的事件与延迟见 `eval/degradation/incident_evidence.json`。

## 为什么打开

按唯一的 `*_api` 事件统计，窗口内有 6 次 timeout（理解 5、记忆提取 1）、6 次成功；连接错误、5xx、429、JSON 解析错误、业务错误均没有对应记录。不能把同一调用的 `phase` 与 `phase_api` 各算一次。理解失败总阶段接近 5 秒上限，其中最后一次 API 执行约 2.03 秒，其余时间包含准入等待；记忆失败的 API 执行约 39.93 秒，并非理解服务的 5 秒上限。

旧实现按 endpoint + model 共用计数器，理解、生成和记忆共用同一个聊天供应商模型，因此相互影响。在线配置阈值 5、打开 30 秒；不是滚动窗口失败率，每次成功清零，每次失败更新打开时间。embedding 与 rerank 使用不同模型，原本独立。

00:49:13 与 00:49:31 的理解请求均直接得到 `circuit_open`；同一窗口还有 12 次记忆提取因共享计数器被拒绝。00:49:50 半开探测再次超时，00:49:52 理解请求成功。旧实现已有单探针与过期租约回收，并非完全没有恢复机制。

## 是否误计，是否要改超时

历史日志只写 timeout，无法区分真实读取超时与父请求预算耗尽；不能据此宣称代理宕机、冷启动或并发就是根因。代码可确认一个分类缺陷：BudgetExceeded（包括用户取消）继承 TimeoutError，会被当作依赖失败累计；JSON/schema 错误在旧 guarded_call 中不累计，但路由器将若干输出质量问题统一报告为 model_unavailable，诊断不准确。

成功理解调用历史样本 889 个，P50 1.946 秒、P95 2.778 秒、P99 3.389 秒。5 秒上限高于观察到的成功样本 P99，保留 5 秒，不靠加大超时或关闭熔断隐藏故障。该分布不含超时截断的真实完成时间，不能声称是全量供应商 P99。

## 隔离与恢复

SQLite WAL 与事务提供跨进程共享状态，不是各 worker 独立计数。问题在于操作没有隔离，且历史只有当前计数器、没有状态转换流水，难以准确复原每次打开时刻。重启也不会清空共享计数。

修复点：按 router_model / main_model / memory_model / embedding / rerank / milvus 隔离；依赖失败分类；滚动窗口最小样本与失败率；有限指数退避、单探针及连续成功恢复；独立记录 429、输出质量问题、内部错误；提供状态、延迟与告警。保留准入、配额、Retry-After 和总请求预算。

## 餐次与验证缺口

断开模型的复现已确认：早餐无法路由，午餐、早饭和晚餐可路由。旧规则遗漏早餐且没有 meal_type；规划器把任何餐次当作通用两菜一汤。修复需要配置词表与餐次模板，不能只加一个词。

`tests/test_degradation_acceptance.py` 在修改业务代码前失败。`eval/degradation/baseline.json` 是同一脚本对原实现的基线：主路径使用脚本化理解结果，不冒充真实模型评测；真实备用路由和本地来源规划参与执行。新餐次字段尚不存在，餐次字段一致性失败不能解释为所有旧午餐菜单都没有价值。最终报告必须用相同方法对照，并另列真实在线验证。

结论：存在真实超时记录（a），取消/总预算可能误计的可达缺陷（c），操作间共享导致连带熔断与恢复观测不足（e）；没有证据需要放宽当前理解超时（b），也没有证据完全缺失半开机制（d）。

## 评测审计更正

S0 的 `baseline.json` 与中间的 `after_s2.json`、`after_s3.json` 在审计中发现缓存隔离缺陷：ok 用例写入理解缓存后，后续故障格命中了缓存。保留原文件供审计；其中 `fallback_correct` 不能解释为真实备用路由正确率，也不得用于计算降级提升幅度。修复前真实 breaker_open 复现的失败测试和历史事故统计仍有效。最终评测按故障隔离缓存，并逐格断言 FaultyModel 调用次数和实际路径。没有未修改源码快照可重跑相同的修正后基线，因此不补造旧备用路径数字。
