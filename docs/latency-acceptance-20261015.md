# 回答延迟诊断与优化 · 2026-10-15

## 根因

service_runtime.request_json 先前将完整请求 JSON 的UTF-8字节数加输出上限当作token预留，中文及长来源内容被大幅高估。限流器每分钟预算60000，在生成和双路复核之间常触发等待，记录中的支持性/完整性复核耗时出现约49～58秒。这个记录当时包含准入和网络时间，不能把它全部归因于模型推理。

此外，成功请求仍按预留值记账，不使用供应商返回的实际 usage；已完成的调用与未用完的输出预算继续占据一分钟窗口。多次提问或需要修正时积累更明显。

## 修改

- 采用已安装 tiktoken 的 cl100k_base 代理估算请求token，加25%余量，并保留输出预算。不是DeepSeek精确tokenizer，不将代理数当供应商计费数。
- 成功响应含有效 usage.total_tokens 时，以请求唯一call_id结算对应预留；不存在、布尔值、负数、非整数均保留原估算。失败调用仍保留保守预留。SQLite calls 表以兼容迁移增加call_id，旧预留不清空，按正常一分钟窗口过期。
- LangChain请求也改为token代理估算；供应商usage结算当前用于JSON请求路径。
- 核验JSON输出预算从2500调整为768；保留生成、支持性核验和完整性核验，保留原文与逐字引用检查。没有放宽TPM、RPM、并发、熔断和取消机制。
- 分别记录 phase_admission 与 phase_api，原有总耗时保留。日志不包含正文和认证头。

## 实测

| 场景 | 用时 | 结果 |
|---|---:|---|
| 修复前页面：基础牛奶面包的酵头怎么制作？ | 62.9秒 | completed / verified |
| 修复后同问题RAG链路 | 3.844秒 | verified / model_generation，3图 |
| 修复后蒸水蛋用什么盖住碗？RAG链路 | 6.181秒 | verified / model_generation |
| 修复后同问题页面全链路 | 13.563秒 | completed / verified，3图 |

页面样本减少约78%。样本不是统计中位数或P95，不承诺所有请求相同耗时。已有Embedding/重排缓存可用，最终答案缓存没有为本次测试专门启用，模型生成和复核仍实际执行。页面包含记忆、路由和排队，不能将其耗时与单独RAG耗时等同。

新遥测显示页面调用的准入等待约0.001～0.003秒，生成API约1.721秒、支持性复核1.104秒、完整性复核1.172秒。该次记忆重排API响应约7.372秒，是真实外部API响应等待，与已修复的本地错误限流分开记录。外部API、实际配额不足和复杂问题的修正仍可能增加延迟。

331项自动化测试通过（开启真实PostgreSQL HTTP集成）。新增5项覆盖中文请求链预算、输出预留与限流继续生效、成功usage结算、无效usage不释放配额、准入/API遥测拆分。实际模型回放仍返回核验通过的回答，没有用未经核验的流式文本作为已完成结果。
