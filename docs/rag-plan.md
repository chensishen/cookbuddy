# HowToCook + Milvus RAG 方案草案

> 这是项目初期的历史方案草案，下面“本轮不启动服务”等措辞描述当时范围。当前已完成全库文本RAG、本地图片来源查询和工具调用MVP，运行入口及真实限制以[项目README](../README.md)和[当前验收](agent-mvp.md)为准。

本文件用于逐步讨论，不代表所有方案已经确定。推进顺序：文本分块 → Embedding → 向量检索 → Rerank。每阶段讨论并验证后，再进入下一阶段。

## 本轮范围

- 下载 Milvus Docker 镜像；版本来自本轮查阅的官方安装脚本：milvusdb/milvus:v3.0.2。
- 使用 HowToCook 规划文本知识库。
- 本轮不启动服务、不全量导入数据、不安装模型、不实现 Agent。

## 数据来源与可追溯性

来源：https://github.com/Anduin2017/HowToCook

优先选取 dishes 下少量、不同长度的 Markdown 菜谱。后续另行加入 tips 中的烹饪技巧，标记不同文档类型。Markdown 可以直接解析标题、列表和链接，首轮无需 OCR 或多模态解析。

正式采集时保存仓库 commit、文件路径、原文、来源链接和内容哈希。保留仓库许可证文件。这样可以复现检索结果、追溯答案、检测更新，避免每次上游变化都重新生成全部向量。

菜谱中的热量、时间等信息只作为来源陈述，不默认经过验证；原文未提供的字段保持未知，不由模型补写成事实。

## 1. 文本分块：当前讨论重点

先建立两个可比较的方案，而不是预先认定分块越细越好。

方案 A：整道菜作为一个块。短菜谱信息完整，适合作为基线；过长文本需要按最终 Embedding 模型的 token 限制处理，不能静默截断。

方案 B：按语义章节形成子块，同时关联完整菜谱：

- 原料和用量放在同一块或显式关联，避免只查到材料却找不到数量。
- 操作步骤保留有依赖关系的连续步骤；步骤下的提示随步骤一起保留。
- 附加技巧可独立成块，但必须携带菜名和章节信息。
- 每块保存 recipe_id、chunk_id、菜名、章节、顺序、来源、文本与处理版本。

Embedding 输入可加入菜名和章节标题；用于审查和引用的原文另行保留。不是只在 metadata 中存菜名，因为 metadata 不会自动进入文本向量。

整篇原文作为父文档保存在文件或结构化文档存储中，Milvus 保存可检索的块及关联信息。完整做法查询可按 recipe_id 取回父文档；局部技巧查询先返回相关章节。父文档回取应控制上下文长度，不自动把所有候选全文都塞入提示词。

先比较约 20 道菜和约 20 个查询；这是讨论用的起始规模。观察是否找到正确菜谱、用量是否完整、步骤是否被切断，再决定分块方式与长度。

## 2. Embedding：分块确定后讨论

选择支持中文检索的模型，结合本机资源、是否允许远程 API、成本与样本效果决定本地或远程部署；本轮不锁定具体模型。

查询和文档使用同一套模型及其规定的输入格式。记录模型版本、维度、token 上限、预处理规则和是否归一化；距离度量按模型要求选择。模型变化可能需要重新建 collection 并重算向量。

先验证“番茄/西红柿”等别名及日常表达的检索效果。别名统一可以辅助匹配，但保留原始名称。向量相似度不能证明食材齐全。

## 3. Milvus 向量检索：先基线，再混合检索

本地开发拟采用 Standalone，具体启动配置在下一次明确执行时完成。当前官方提供单容器嵌入式部署方式，可减少本地初始服务数量。固定版本便于复现。

第一轮使用单个 dense 向量字段，建立最小可观察的检索基线。候选字段：chunk_id、recipe_id、title、section、text、source_path、source_commit、embedding。

食材推荐还需要结构化食材信息：原始名称、规范名称、必需/可选、主料/调料。必须从原文提取或人工核查，不默认所有菜谱都明确标注这些属性。推荐时比较缺少的材料，并与用户约定家中常备调料范围。

记录 Top-K 候选及其分数，按菜谱去重，防止一道菜的多个块占满结果。小样本阶段可以用精确搜索作为对照，扩大数据后再讨论近似索引及参数。

当纯向量检索漏掉菜名或关键材料时，再加入 BM25 与 dense 混合检索，并验证中文分词效果。Milvus 支持多向量混合检索，所以可以在同一系统中开展这项对比。

## 4. Rerank：在召回可用后引入

召回先取一批候选，再由独立的 query-document Rerank 模型精排。模型选型与输入长度后续讨论。先在子块层精排、按菜谱聚合，再按问题取回完整菜谱，是一个待验证方案。

Milvus 中 RRF 或加权融合是合并多路检索排名，与阅读查询及候选文本的语义 Rerank 模型不同。两者分别验证，不能把融合排名当成已经完成语义精排。

Rerank 无法找回没有召回的菜谱，也不代替食材约束检查。比较引入前后的前几名相关性、延迟以及缺少材料的推荐情况。

## 验证问题与下一步

验证问题覆盖：菜名查询、食材组合推荐、步骤/技巧查询、别名表达、不存在于库中的菜谱。正确结果由我们查看原文共同确认。

下一步仅讨论文本分块：拿一短一长两份真实菜谱，列出整篇方案与章节方案的实际块，检查查询需要哪些信息，之后再决定是否实现分块脚本。
