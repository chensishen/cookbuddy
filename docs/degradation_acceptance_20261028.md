## 实际页面

Chrome 新对话“帮我安排早餐”返回主食、配菜与饮品，首轮显示耗时；原页面继续更换菜单后，早餐保留，换成“吐司果酱、炒滑蛋、奇异果菠菜特调”，显示 5.5 秒，无错误降级横幅。页面可继续使用，服务保留在本地 8080 端口。

真实 API 菜单请求 P50/P95 为 5.617/6.113 秒，样本仅 7 条，不能推断生产 SLA。离线故障路径 P50/P95 为 317.936/840.22 毫秒，慢响应使用异常注入，不代表供应商延迟。

## 发现后继续修复的项目

1. 真实模型返回未指定的菜汤数量为 null，触发旧整数校验。现只在未明确组合时归一为模板内部占位值；明确数量仍严格校验，新增回归已通过。
2. 生成回答未通过核验与服务故障需要区分提示；候选原文现在保留逐字核对的完整证据，不把片段生成的结论冒充已核实事实。
3. 准备阶段失败原先丢失耗时与请求编号，现保存耗时、固定错误类别和不含异常正文的诊断位置，并向页面提供请求编号。
4. 旧队列测试用 5 毫秒墙钟判断非阻塞，在高负载下误失败。改为挂起实际后台写入，验证提交返回后后台任务仍未完成，更直接检查原来的非阻塞要求。

## 保留的限制与审计

- 真实 API 的 11 条结构检查通过，不代表 11 条语义完整回答全部通过。其中 1 条复杂烘烤问答的生成阶段超时，返回带来源和请求编号的候选原文，未生成完整温度/时间/调整结论。这项仍是受限结果。
- 并行评测高负载时出现准备阶段 deadline；原始失败保存在 `live_final.json`。后续减少并行负载后，核心菜单请求复测通过；未调大准备预算来隐藏问题，也不能保证高负载和外部服务异常下所有请求均成功。
- 原 `baseline.json`、`after_s2.json`、`after_s3.json` 故障轮受到正常轮缓存污染，已标记不能用于降级率前后比较。修正评测采用按故障隔离缓存与调用断言，不伪造修复前百分比。
- 本地能力不使用向量/精排服务时，矩阵验证未调用故障边界；不能据此声称覆盖了所有远程检索故障的生成结果。
- `/health` 给出监控指标和配置告警，目前降级比例的分母为持久化完成的请求；未部署外部通知平台。
- 人数、时间、难度不写入长期偏好的要求保持，并由原有相关回归保护。
