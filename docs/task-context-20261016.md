# 推荐任务的会话上下文修复（2026-10-16）

## 问题

实际失败对话为“我喜欢吃辣的，给我推荐几道菜”→“鸡肉”。原记录显示，多轮问题曾正确展开，但路由强制询问库存，生成提示又要求所有食材推荐采用“已有、缺料”的格式，与禁止编造库存的校验冲突。仅靠拼接历史文本无法保证推荐、检索和校验始终使用同一个任务。

## 实现

- `scripts/cookbuddy/task_context.py` 保存版本化的推荐状态：推荐方式（口味/食材条件与明确库存分开）、食材、口味、排除做法、其他限制、数量及实际推荐列表。支持本轮新增条件、替换食材、明确菜名开启独立任务、按序号追问已展示结果。
- 状态随 assistant 的 `record.task_context` 存在 PostgreSQL；读取当前用户、当前会话、当前用户消息之前的最近 assistant 记录。显式空状态是任务边界，不向更早的推荐任务回溯。无需新增表或前端配置。
- “鸡肉”“改成牛肉”是食材条件，不自动证明用户拥有库存。“第二道怎么做”绑定上轮实际通过校验并展示的第二道菜名及来源，而非让模型猜测序号。
- 支持的简单推荐条件由 `preference_recommendation.py` 对完整活动菜谱集筛选：逐字核对当前文件和章节，检查主食材家族、原文加辣依据与制作方式。每个候选保留原文证据。排除油炸采用保守策略：相关操作中出现“炸”的候选被排除；因此也可能排除空气炸锅菜谱。可选加辣单独说明，不推断精确辣度。
- 未覆盖的限制（例如过敏、低盐、复杂设备或预算要求）保留在状态及展开问题中，回到原 RAG 处理，不能用简单规则忽略这些限制后返回“通过”。本次不是任意自然语言条件的完整推理器。
- 已明确的任务更新使用注册表目标直接路由，不再重复调用记忆向量检索、意图 LLM 和意图 Embedding。独立新问题仍使用原 Hybrid Router；明确要求“按我的口味”等个性化请求仍读取记忆。
- 修改通用生成提示：按口味推荐无需声明库存、无需展示完整配方，可以按用户要求推荐多道菜。仅明确库存才核对缺料。禁止编造库存的校验仍保留。
- 前端口味推荐卡片只显示菜名、匹配理由及一张可用原图，不使用原料覆盖率、已有/缺料格式；校验说明放到折叠依据内。
- 为序号追问绑定来源后，原文兜底仍能识别纯“怎么做”请求；只去除与已选来源完全一致的程序绑定后缀，来源约束本身仍有效。

## 验收

387 项 Python 测试通过，包含 PostgreSQL 集成；19 项前端测试通过。覆盖：增加条件、替换食材、否定口味、未知约束保留、失败结果不生成序号列表、明确新任务边界、序号无列表时澄清、当前原文逐字一致、伪造/陈旧内容拒绝、刷新和新 Store 对象恢复、用户及会话隔离、已知任务不调用意图模型。

真实页面中连续输入：

1. “我喜欢吃辣的，给我推荐几道菜”：直接返回 3 道菜。
2. “鸡肉”：返回凉拌鸡丝、宫保鸡丁、干煸仔鸡，保留加辣依据。
3. “不要油炸”：保留鸡肉与辣味，候选变为凉拌鸡丝、宫保鸡丁、红烧鸡翅。
4. “第二道怎么做”：精确打开宫保鸡丁及其原文来源；生成摘要被拒绝时，交付通过逐字核验的原文制作内容。
5. “改成牛肉”：保留辣味与非油炸，返回孜然牛肉、小炒黄牛肉、尖椒炒牛肉。

前四轮测试发生在移除重复记忆/意图调用之前，总耗时分别为 8.546、3.781、2.861、146.020 秒。第四轮中记忆检索约 32 秒、意图向量匹配约 53 秒、RAG 检索约 47 秒；此慢样本保留，没有隐去。完成任务直接路由后，第五轮真实总耗时为 0.589 秒。直接推荐不需要远程生成；具体菜谱做法仍需原 RAG，外部 Embedding/生成服务的慢响应未由本次上下文修改彻底解决。

## 手动复测

刷新页面，新建对话后按上述五句逐句发送。再新建另一个对话，仅发“第二道怎么做”，应要求给出菜名，而不是引用上一个会话。回到原会话后发送一个独立菜名的做法问题，原推荐任务应关闭。复杂未覆盖条件仍可能受原 RAG 的可靠性和响应时间限制。
