# 图片与其他附件处理：第一批样本

## 本轮结果

完成全量图片来源索引和三张本地图片的解析试验。正式菜谱中有354张本地图片：213张JPG、96张JPEG、42张PNG、3张WebP；349处本地引用全部定位成功，另有2处远程引用、8张未引用图片。本目录未发现PDF、Word、音频或视频附件，因此没有虚构这些类型的解析结果。

来源索引保留原图路径、SHA-256、菜名、章节、Markdown行号、逐字图片引用、图注和原有文本块ID。相同文件内容可以按哈希共用OCR缓存，各菜谱与章节的引用关系仍分别保留。远程图片保留链接，没有下载；未引用图片保留在索引中，不猜测对应做法。

三张样本均来自基础牛奶面包：

| 样本 | 处理结果 | 不能据此推断 |
|---|---|---|
| 设备简介 | OCR识别出一个编号“①”，置信度约0.3；另保存工具布局的看图描述 | 编号不是用量；喷瓶内液体成分和工具容量无法仅凭照片确认 |
| 发酵前酵头 | OCR未识别出文字；保存碗中混合物的外观描述 | 发酵是否成功、温度和配比 |
| 面包成品 | OCR未识别出文字；保存颜色、表面开口和摆放状态 | 内部熟度、烘烤温度和时间 |

共生成4个独立解析块：3个视觉描述块、1个OCR块。图片解析没有改动原文、旧分块、Embedding或Milvus。所有新块enabled=false，仍是解析草稿，未进入正式问答。

## 为什么分开保存

图注是作者写在Markdown里的文字，OCR是程序识别的文字，看图描述是对可见内容的解释。这三种证据不能混为逐字原文。每个解析块标记evidence_type，同时关联图片文件和原文中的引用行；问答引用图片时，应展示原图与具体来源，而不能把描述包装成菜谱原句。

本机使用Apple Vision进行OCR，保存文本、置信度和区域坐标，不调用此前受限的硅基流动接口。[Apple官方文档](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)说明此请求用于识别图中文字。这里保留实际返回，低置信度区域单独标记；没有识别到文字也是有效结果，不用模型补写“识别文字”。

三张视觉描述由助手实际看图后整理，并用图片哈希绑定。它不是视觉模型API的批量解析，也不表示用户已经全面核对。照片没有直接给出的温度、时间、重量、口感或熟度保持未知。

先产生可检查的文字解析块，便于之后使用已有文本检索流程。这与图片向量是不同步骤；仅上传图片向量不能替代OCR或让文字回答自动获得图片证据。本轮没有更换Embedding模型。

## 文件与运行方式

- `data/processed/media_pilot/asset-index.json`：全量附件及章节关联。
- `sample-descriptions.json`：三张已看图样本的描述、限制及图片哈希。
- `ocr-cache/`：按图片哈希保存本地OCR原始结果，并记录OCR程序版本哈希。
- `parsed-images.json`：合并解析记录，保留失败信息、OCR审核状态和启用状态。
- `media-chunks.jsonl`：分别标记image_ocr和visual_description的解析草稿。
- `review.md`：原图、描述、实际OCR返回和原文位置。

在项目目录运行：

```sh
python3 scripts/process_recipe_media.py
```

默认处理这三张样本，`--limit 1`或`--limit 2`可缩小批次。重复运行复用图片及程序哈希一致的OCR缓存。需要macOS的Vision与Swift工具链；其他系统须更换OCR后端，不能假定已支持。当前脚本不自动为其他351张图片生成视觉描述。

67项项目测试通过，包含图片路径边界、引用行与图注匹配、OCR区域和置信度、图片变更、两类证据隔离。三张真实图片的OCR运行成功；这不代表全量图片识别准确率。

## 其他文件类型与后续研究

Markdown正文继续按副标题分块；图片引用及表格、列表、代码等原文保留。此轮没有把未出现的文档类型接入解析器。

后续新增PDF需保留页码，Word需保留标题/段落与表格位置，音视频需保留时间位置；解析失败或尚未支持的类型须明确记录。图片后续可以扩充照片样本与文字截图样本，核对解析错误后再研究视觉API、图片向量及独立集合检索，避免把设备编号和背景文字当作配方事实。
