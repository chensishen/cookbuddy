# 429共享冷却修复（2026-10-20）

本步完成调用治理中的一个可复现缺口：供应商返回429和有效 `Retry-After` 后，同一供应商/模型的实际API请求共同遵守冷却时间。577项后端测试全部通过，无跳过；本步未请求真实供应商制造429，未修改账号配额或历史评测分数。

## 原因

原实现只在收到429的当前调用中等待 `Retry-After`。当它不再重试或其他进程同时请求时，共享运行库没有保存供应商的等待要求；其他调用仍可能继续发送请求，加重限流。已先编写失败回归复现：首个调用收到10秒等待要求，第二个调用仍执行了API函数。

这证明了代码缺口，不能证明历史封存测试中的所有429都由它导致。历史错误未完整记录该响应头，账号RPM/TPM仍为用户确认的“未定”。

## 修复

- SQLite运行库新增 `provider_cooldowns` 表，按现有供应商/模型scope持久化冷却截止时间，跨阶段、跨进程生效；已有数据库自动建表。
- 即使当前调用没有剩余重试次数，仍记录有效等待要求。并发收到多个等待要求时保留较晚的截止时间；先前在途请求成功也不会清除冷却。
- 准入检查先遵守供应商冷却，阻止实际HTTP请求；冷却超过剩余预算时直接退出，让调用方进入原有降级流程。原有取消、总预算、并发/RPM/TPM和熔断约束继续生效。
- 冷却到期后仍遵守熔断状态；已熔断模型只允许一个半开探测，成功后恢复。
- 支持秒数和HTTP日期；无效、NaN或Infinity不会写入冷却。缺少有效响应头时继续采用原有限重试与熔断，不猜测账号配额。
- 诊断事件记录 `provider_retry_after` 等待原因，不记录请求正文、密钥或供应商响应正文。

代码：`scripts/service_runtime.py`。恢复过程不需要清理缓存或删除运行库。
